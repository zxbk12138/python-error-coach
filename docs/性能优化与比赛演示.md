# 性能优化与比赛演示

## 为什么简单问题会慢

实机测试中：

- 简单 `NameError` 可以在一小段时间内回答；
- 需要调用工具、执行测试并渲染结果时，耗时明显增加；
- 第三方未知库可能触发长时间检索和多轮推理。

延迟的主要来源不是安装 Skill 本身，而是：

- 为简单问题建立不必要假设；
- 运行代码并展示测试结果；
- 加载暂时无关的参考资料；
- 在长上下文中继续处理多个案例；
- 第三方库缺少版本和 traceback 时仍继续推理。

## 快速路径

以下问题只要有明确报错且无冲突证据，直接回答，不运行代码：

- 缺冒号；
- 缩进错误；
- 文字缺引号；
- 变量未定义或拼写错误；
- 字符串与整数混用；
- f-string 缺 `f` 或 `{}`；
- 列表索引越界；
- 函数缺少 `return`；
- 字典键不存在。

快速路径不建立多个假设，不加载详细参考资料，输出“问题一句话、代码块、验证一句话”。

## 完整诊断路径

只有以下情况进入完整流程：

- 存在两个以上合理解释；
- 报错依赖实际运行结果；
- 第三方库或环境问题；
- 用户明确要求深入讲解；
- 多轮反馈改变了原判断。

## 比赛建议

现场或视频主流程建议使用：

1. 简单 `NameError` 或缺少冒号，展示快速路径；
2. 修改后出现新错误，展示反馈更新；
3. 真实课堂列表顺序问题，展示多轮判断；
4. 未知库问题作为备用复杂案例。

不建议把耗时两分钟以上的第三方环境排查作为唯一主演示。

## 演示前准备

- 每个案例单独新建任务，减少历史上下文；
- 提前用 `@` 选中技能，确认出现“加载技能”；
- 先做一次预热，避免首次加载和客户端初始化影响录屏；
- 简单案例要求“直接修”，避免模型自行展开教学；
- 视频可剪掉纯等待画面，但保留真实输入、技能加载和最终输出。

## 验收目标

- 单点错误：优先控制在 15 秒以内；
- 多轮反馈：优先控制在 30 秒以内；
- 复杂问题：尽量控制在 60 秒以内；
- 任何超过 90 秒且无法中断的场景，不作为现场主流程。

速度不是评分表的独立项目，但会影响实际体验和“实用价值”的呈现。稳定、正确的 30 秒回答优于为了快而猜测。
