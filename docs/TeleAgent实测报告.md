# TeleAgent 内置模型实测报告

## 测试环境

- 客户端：TeleAgent 3.0.1 桌面端
- 模型：客户端当前选中的内置模型
- 技能版本：`python-error-coach` 2.2.0
- 导入结果：删除旧条目后重新导入成功，安全审查通过并默认启用
- 测试方式：新建任务、输入真实问题、等待任务完成并检查回答

## 已验证能力

- 技能能够被内置模型加载；
- 零基础问题使用生活化、短提示；
- 基础类型问题能定位到具体表达式；
- 中阶问题不再重复基础定义；
- 进阶问题能进入迭代器机制；
- 回答总体保持“先事实、再检查、再验证”的结构；
- 没有在前四个案例中直接输出整份作业代码。
- 多轮测试中能够接受新证据、结束已修复分支并转入新错误；
- 补充关键上下文后能够撤回原假设，改为新的诊断方向。
- 能够区分“直接修”和“带着学”，不会对所有请求使用同一种互动方式；
- 修复后能做轻量掌握验证，同时尊重用户只求快速修复的意图。
- 简单问题保持短回答，不再机械套用固定标题；
- 修改代码时能够遵守最小改动范围，不顺手重构无关内容。

## 发现的问题

### 第三方库门禁有效，但模型仍可能做合理推断

T5 中模型使用了“大概率不是 CUDA 坏了”这种判断。虽然语气不是绝对，且方向很可能正确，但在缺少库名、版本和完整 traceback 时，没有严格按照 2.1.0 的“第一轮只收信息”执行。

T6 使用虚构库验证后，模型明确拒绝猜测参数，说明面对真正未知的 API 时兜底有效。

当前结论：

- 不应把“第一轮绝对不许推断”作为唯一验收要求；
- 模型可对报错信息中已经明确出现的 API 名称做有条件判断；
- 真正未知的库和泛化错误必须停止猜测；
- 在展示中同时保留 T5 和 T6，能说明系统不是机械拒答，也不会乱编 API。

### 客户端临时渲染空白

首次提交后主内容区曾短暂空白，重启客户端后任务与历史恢复。该问题发生在客户端渲染层，不是技能逻辑错误；最终任务可正常完成。
